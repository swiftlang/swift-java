
# swift-java jextract

Automatic Java wrappers for existing Swift code, generated by `swift-java jextract`.

## Overview

`jextract` is the *Java source-generation* part of swift-java. It is similar in
spirit to the JDK's [`jextract`](https://github.com/openjdk/jextract/), but it
consumes Swift rather than C headers.

**No code changes** need to be made to the Swift libraries you want to expose.
The outline of the approach is:

- Swift sources are compiled to `.swiftinterface` files.
- Those `.swiftinterface` files are read by `swift-java jextract`, which
  generates `*.java` files.
- The generated Java files contain the code for efficient native invocations.

You can then use the Swift library from Java by calling the generated methods
and initializers.

You can always use the command line `--help` to get additional guidance about the tool and available options:

For the set of Swift language features that can be extracted, and what each one
looks like on the Java side, see <doc:FeaturesJextract>.

### Modes

jextract can generate bindings in one of two modes, `jni` or `ffm`. See
<doc:FeaturesOverview> for guidance on choosing between them.

> Tip: To use the `ffm` mode you need JDK 25+, because it relies on
> [JEP 454: Foreign Function & Memory](https://openjdk.org/jeps/454) APIs. The
> simplest way to install a JDK distribution of your choice is
> [sdkman](https://sdkman.io):
>
> ```bash
> curl -s "https://get.sdkman.io" | bash
> sdk install java 25-open
>
> export JAVA_HOME=$(sdk home java 25-open)
> ```

### Default jextract behaviors

Only `public` functions, properties and types are imported.

Global Swift functions become static functions on a class with the same name as
the Swift module in Java:

```swift
// Swift (Sources/SomeModule/Example.swift)

public func globalFunction()
```

becomes:

```java
// Java (SomeModule.java)

public final class SomeModule ... {
    public static void globalFunction() { ... }
}
```

### Choosing what to export

`@JavaExport(false)`, from the `SwiftJavaAnnotations` module (also re-exported by `SwiftJava`), keeps a
public declaration out of the Java bindings. On a type or an extension it applies to all their members:

```swift
import SwiftJavaAnnotations

public struct Session {
  public var token: String
  @JavaExport(false) public var debugDump: [String: Any]
}

@JavaExport(false)
extension Session {
  public func swiftOnlyHelper() -> (Int, String) { ... }
}
```

With `"exportMode": "annotated"` in `swift-java.config`, jextract does the opposite: it exports only
declarations marked `@JavaExport`, and the members of a type or extension marked `@JavaExport`. A type
that isn't marked is still exported, with only its marked members, when one of its members is marked.
An extension's members are exported only when the extended type is exported too.

Declarations that aren't exported are never translated, so Swift-only API that has no Java
mapping doesn't produce warnings or generated code.

### Main actor in Java-hosted processes

Swift libraries may use the main actor in their public APIs or internally.
When calling Swift from a Java-hosted process, you may need to integrate
Swift's main executor with the host's event loop.

Without appropriate integration, work scheduled on the main actor may not
execute, leaving asynchronous calls incomplete. The required integration
varies by platform and host configuration. For Android, see <doc:Android>.
